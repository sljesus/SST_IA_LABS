# Plan: Corregir Clasificación de Sender Type en Mensajes de n8n

## Problema Identificado
Los mensajes que llegan de n8n con remitente "FAQs" se están guardando con `sender_type: "cliente"` cuando deberían ser `sender_type: "bot"`. Esto causa que aparezcan en el lado izquierdo (cliente) en lugar del lado derecho (agente/bot).

Datos de ejemplo:
- Mensaje de "Jesús Salazar": `sender_type: "cliente"` ✅ CORRECTO
- Mensaje de "FAQs": `sender_type: "cliente"` ❌ INCORRECTO (debería ser "bot")
- Mensaje manual de "agente": `sender_type: "agente"` ✅ CORRECTO

## Investigación Necesaria

### 1. Cómo n8n Guarda los Mensajes
- **Hipótesis**: n8n inserta directamente en la tabla `mensajes` sin usar las funciones de `db.ts`
- **Investigación**: Revisar el workflow de n8n para ver cómo guarda los mensajes entrantes
- **Acción**: Examinar si n8n usa una API personalizada o inserta directamente

### 2. Lógica de Detección Actual
- **Función**: `detectSenderType()` en `lib/constants.ts` incluye "FAQs" en `KNOWN_AGENTS`
- **Problema**: Esta función no se ejecuta cuando llegan mensajes de n8n
- **Verificación**: Confirmar que `KNOWN_AGENTS` contiene "FAQs"

### 3. Flujo de Mensajes
- **Recepción**: Los mensajes llegan de WhatsApp → n8n → Base de datos
- **Almacenamiento**: n8n debe usar `messageService.receive()` con detección correcta
- **Clasificación**: Aplicar `detectSenderType()` al guardar

## Soluciones Propuestas

### Opción 1: Corregir Workflow de n8n
- Modificar el workflow de n8n para usar `sender_type: "bot"` cuando remitente es "FAQs"
- Ventaja: Corrección en origen
- Desventaja: Requiere modificar n8n

### Opción 2: Trigger de Corrección en Base de Datos
- Crear función que corrija `sender_type` automáticamente al insertar
- Usar trigger de PostgreSQL o función en Supabase
- Ventaja: Corrección automática sin tocar n8n
- Desventaja: Complejidad adicional

### Opción 3: Endpoint de Reclasificación
- Crear API que reclasifique mensajes existentes
- Actualizar mensajes históricos con sender_type correcto
- Ventaja: Solución inmediata para datos existentes
- Desventaja: No previene futuros errores

### Opción 4: Webhook de Recepción
- Implementar webhook en Next.js para recibir mensajes de WhatsApp
- Usar `messageService.receive()` con detección correcta
- Ventaja: Control total sobre clasificación
- Desventaja: Reemplaza funcionalidad de n8n

## Recomendación
**Opción 4 (Webhook)** es la más robusta porque:
- Asegura clasificación correcta desde el inicio
- Mantiene consistencia con el código existente
- Permite mejor control sobre el flujo de mensajes

## Pasos de Implementación

### Fase 1: Investigación
1. Confirmar cómo n8n guarda actualmente los mensajes
2. Verificar configuración del workflow de n8n
3. Probar función `detectSenderType()` con "FAQs"

### Fase 2: Implementación del Webhook
1. Crear endpoint `/api/whatsapp/webhook`
2. Implementar verificación de Meta
3. Procesar mensajes entrantes con clasificación correcta
4. Integrar con sistema existente

### Fase 3: Migración de Datos
1. Actualizar mensajes existentes con sender_type correcto
2. Verificar consistencia en la interfaz

### Fase 4: Testing
1. Enviar mensajes de prueba desde diferentes remitentes
2. Verificar clasificación en interfaz
3. Confirmar funcionamiento con n8n

## Riesgos y Consideraciones
- **Compatibilidad**: Asegurar que el webhook no interfiera con n8n
- **Duplicación**: Evitar mensajes duplicados si ambos sistemas procesan
- **Configuración**: WhatsApp debe apuntar al webhook correcto
- **Seguridad**: Implementar verificación de Meta apropiada
